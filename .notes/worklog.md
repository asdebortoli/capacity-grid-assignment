# Worklog

Running notes on how this got built — decisions, assumptions, dead ends, and anything
left unfinished. Append as you go; a line or two per entry is right.

---

- Agreed with Alexandre: weeks start Monday, and only Monday-Friday contribute allocated hours. Assignment start and end dates are inclusive; weekend dates remain valid but contribute no hours, including for weekend-only assignments. The brief leaves working-day rules unspecified, so this is our documented domain assumption.
- Agreed with Alexandre: respect the exact selected date range, including partial weeks. Prorate capacity as weekly_hours / 5 times the selected weekdays in each week, assuming evenly distributed daily capacity; clip allocation to those same dates and label partial weeks in the grid. The saved weekly capacity stays unchanged.
- Agreed with Alexandre: zero weekly capacity is valid. Compare hours directly: positive allocation against zero capacity is over-allocation, while zero allocation against zero capacity is shown as no capacity/no allocation. Do not show a utilization percentage when capacity is zero.
- Agreed with Alexandre: editing weekly capacity changes the person's single setting for all weeks, including past weeks; assignments remain unchanged and partial-week capacity is recalculated. Label the person-level control "Weekly capacity". Effective-dated capacity and historical values are outside the fixed schema.
- Agreed with Alexandre: the backend calculates weekly allocation and capacity. After a successful capacity PATCH, refetch the currently selected range and render the returned values without reloading the page. Prefer this consistent server-calculated result over optimistic updates and duplicated frontend calculations.
- Agreed with Alexandre: GET capacity returns top-level weeks (weekStart, from, to, workingDays) and people (id, name, weeklyHours, weeks). Each person's week contains weekStart, allocatedHours, and capacityHours. Include every person/week even with zero allocation; PATCH accepts {"weeklyHours": number}.
- Agreed with Alexandre: require valid YYYY-MM-DD range dates with from <= to and at most 366 inclusive calendar days; single-day and weekend-only ranges are valid. Weekly capacity must be a provided finite number from 0 through 120, with decimals allowed; missing/null values are invalid. These upper limits are our choices, not brief requirements.
- Agreed with Alexandre: invalid input returns 400, an unknown person returns 404, and unexpected failures return a generic 500 with details logged server-side. Preserve edits after a failed save. If saving succeeds but refetching fails, distinguish that state and offer a refresh retry.
- Agreed with Alexandre: date selection uses draft From/To values and an Apply action; the grid keeps a clearly labeled applied range until submission. Previous/Next week shift both applied dates by seven days, preserving the range length. App owns the applied range and passes it to CapacityGrid; retain the starter's initial 2025-12-29 through 2026-01-16 range.
- Agreed with Alexandre: use a small set of shadcn/ui components (Calendar/Popover, Button/Input/Label, and Table) for consistent controls and less custom UI work. Configure the calendar to start Monday with weekends selectable; preserve Apply behavior. Accept the frontend setup/dependencies while retaining custom capacity logic and the fixed Docker/database environment.
- Capacity query: repeated-looking seed assignments have distinct IDs and are counted independently. Use a bounded calendar-date series and PostgreSQL numeric aggregation, preserving people/weeks with no allocation. Dates stay timezone-free; numeric totals are converted to JSON numbers only after calculation.
- Step 1 verified with Go tests against the unchanged seed, go vet, a Docker API rebuild, and live HTTP/proxy requests. Checked overlapping assignments (Dee: 45/40 hours), partial weeks (Dee: 28/24), zero capacity (Eli: 20/0), weekend-only ranges, inclusive endpoints, year boundaries, invalid dates/ranges, and generic database errors. The 366-day boundary returns 500 people x 54 weeks. Integration tests opt in via CAPACITY_TEST_DATABASE_URL; the command is documented in api/capacity_test.go.
